# Shree Ram Jewellers production launch checklist

This is a release review for `shreeramjewellers.store`. Every checkbox starts open. The assigned person should record the environment, build revision, date and outcome for each check. Keep customer details, photos, tokens and credentials out of the evidence.

## Required for the public showroom

| Gate | Responsible | Evidence to accept |
| --- | --- | --- |
| [ ] Domain and hosting | Owner + hosting operator | Confirm domain control, approved canonical host, DNS target and certificate renewal. Verify HTTPS, redirects from HTTP and any alternate host, and a stable same-origin route from the web application to the private API. Record the previous working deployment and rollback procedure. |
| [ ] Production runtime | Hosting operator | Use the project's supported Node version and lockfile. Verify production-mode builds for both workspaces, supervised web/API processes, private service connectivity and restart behaviour on a staging equivalent. Verify the API's loopback bind suits the selected service layout. |
| [ ] Configuration and secrets | Hosting operator | Review only the variable names and injection scopes in the release record. Confirm production mode, the exact HTTPS web origin, the private API origin, provider account separation and restricted access to owner/session and service credentials. Inspect public bundles, responses, logs and source maps for accidental secret disclosure. |
| [ ] Data readiness and recovery | Separate database operator | Independently confirm the intended operational instance, schema readiness, least-privilege access and approved catalogue records. Supply evidence of an encrypted backup and a successful restore into an isolated destination. Agree recovery time, acceptable data loss, retention, restoration owner and last verified backup time. Keep database investigation and repair with that operator. |
| [ ] Permissions and caching | Engineering + hosting operator | Through the actual proxy/CDN, verify unauthenticated owner requests fail, session expiry/logout revoke access, production cookies use HTTPS restrictions and invalid mutation origins are rejected. Test authenticated owner responses, CRM receipts/status, private media and API error responses for cross-user cache leakage. Use separate browser sessions. |
| [ ] Rate limits and traffic | Engineering + hosting operator | Map the proxy chain and trusted hop count. Confirm the edge strips spoofed forwarding headers. Load isolated staging with concurrent visitors, including server-rendered catalogue requests sharing a server's outgoing address. Verify genuine visitors can browse, abusive submissions receive 429, and limits cover all replicas. Record the tested client/SSR traffic path and capacity. |
| [ ] Catalogue, media and business content | Owner + engineering | Approve actual SKUs, descriptions, public prices or enquiry-only state, inventory, categories and collections. Check that drafts, archived pieces and hidden-category products stay private. Review the approved homepage in its populated, empty and unavailable states. Verify the showroom address, customer contact, WhatsApp destination, hours, map and social destinations wherever published. Record unprovided items as pending. |
| [ ] Cloudinary | Media operator + engineering | Verify the approved account, server-only upload credentials, allowed delivery domain, image quotas and limits. With approved disposable staging media, test upload, invalid/oversized bytes, replacement, order, alt text, display and removal. Inspect the cleanup queue after both successful and failed remote deletion. |
| [ ] Enquiries and appointments | Owner + QA | Using consented staging requests, test product/custom/general enquiries, appointment requests, receipt lookup, owner review and customer-visible status. Confirm an appointment only through the authorized owner flow. Check out-of-hours and full-slot rejection, private note isolation, invalid receipt handling, outage feedback and a submission interrupted before its response. |
| [ ] Communication and account access | Owner + operations | Assign someone to monitor the dashboard and follow up on submissions. Current CRM flows store requests and expose status. Automated email delivery and owner password recovery require separate functionality. If either is required for launch, approve its design, configure its provider separately and demonstrate delivery or recovery end to end in staging, including expired tokens and provider errors. Record how owner access is recovered operationally. |
| [ ] Privacy and customer terms | Owner + designated reviewer | Finish the owner questions in both review drafts. Confirm actual hosting/providers, CRM retention and handling of customer requests, then approve the final wording and publication date. Verify the published customer-facing destinations and consent text correspond to the enabled features. |
| [ ] Navigation and accessibility | QA | On desktop, phone and tablet, follow catalogue searches/filters, product details, galleries, collection links, wishlist, WhatsApp enquiry and appointment actions. Check keyboard navigation, visible focus, mobile menu dismissal, screen-reader form errors, slow/unavailable API behaviour, image fallbacks and overflow. Confirm customer actions stay usable when an optional related request fails. |
| [ ] Search visibility | Engineering + owner | Check HTTPS canonical URLs, titles and index policy for public pages, robots rules and sitemap contents. Verify admin, credentials, private status/preview resources and development/staging hosts cannot enter public discovery feeds. Verify a curated product URL in the final host's actual response. |
| [ ] Logging, monitoring and rollback | Hosting operator | Monitor process liveness separately from database-backed readiness, plus API errors, latency, rate-limit responses, queue backlog, disk usage, provider failures, certificate and backup health. Test an alert reaching its owner. Inspect logs and monitoring traces for headers, private URLs, query tokens, form bodies or photos. Rehearse application rollback in staging and coordinate any data recovery with the database operator. |

## Additional gates for optional features

- [ ] **AI photo try-on.** The owner and provider operator approve the Gemini project, model access, data-use terms, region, billing limits and selected products. QA uses an authorized test image to verify consent, result ownership, expiry, early deletion, resumed polling after a lost response and recovery from provider failure. Test worker interruption and restart, restricted private storage outside public/backup paths and eventual cleanup. Leave photo generation disabled pending acceptance.
- [ ] **Live camera.** The owner approves transparent assets and placement for eligible pieces. QA exercises permission denial, start/stop, camera switching, backgrounding and tracking loss on supported physical iOS and Android devices. Confirm live frames stay on the device and that camera tracks terminate. Publish only the capability demonstrated on the tested devices.
- [ ] **Third-party contact and delivery.** The owner verifies every external contact destination that will appear. If automated email becomes an approved feature, verify sender identity, domain authentication, delivery to a controlled mailbox, failure handling and monitoring. A configured mail credential alone is insufficient evidence of delivery.

## Release decision

The release owner records the named approvers, completed gates, enabled optional features, remaining issues and the person authorized to roll back. Deploy only after separate approval. Repeat the approved smoke checks against the deployed build with permission for any action that creates a real record or sends a message.
